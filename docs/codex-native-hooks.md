# Native Codex parent connection

Tested with Codex CLI 0.160.1 and the actual Codex desktop chat on 11 October 2026. Save installs managed entries in `$CODEX_HOME/hooks.json`, preserving unrelated hooks with a backup and atomic replacement. Symlinked hook files are refused. Codex requires review of the exact hook definition in `/hooks`: installing configuration does not grant trust. In the desktop test, the user approved the four hooks in the existing chat and live instructions arrived on the next user message without an app restart.

SessionStart and UserPromptSubmit inject live rules and a CLI command containing this parent's exact session ID and working directory. PostToolUse injects ready results. Stop waits up to 205 seconds for outstanding work, then requests continuation with completed results. Remaining jobs are explicitly reported as pending after that deadline; the continuation does not repeat a long wait. This is active-turn continuation, **not idle wakeup**. On the next user turn, pending results are collected. The official [Codex hook documentation](https://learn.chatgpt.com/docs/hooks) describes native trust and continuation semantics.

A local, detached session service owns one persistent worker host. Each delegate creates a worker conversation; message uses a prior job ID to queue the next turn in that same conversation. The parent's shell invocation returns immediately. A token-protected loopback endpoint and on-disk jobs are scoped by parent session ID plus folder. Services expire after 30 idle minutes. Worker context is retained while that service is alive; restarting a service never replays uncertain work and marks interrupted jobs with an unknown outcome.

Result delivery is claimed atomically inside the service before emitting hook output, preventing competing hooks from delivering the same result twice. Codex does not acknowledge hook-context ingestion back to this service. If a hook dies after its delivery claim, `status` retains the completed result for recovery; the service does not automatically replay it. Queued messages do not interrupt a currently running worker.

Both hook execution and native CLI operations check the resolved Codex CLI version and fail closed outside 0.160.1. This checks the executable resolved in the hook environment, not an independently proven desktop backend identity. Different desktop and PATH CLI versions need separate compatibility verification. Managed Codex parents set an environment marker that disables native hooks, avoiding duplicate integrations.

Actual desktop acceptance: in the existing `Assess cross-agent orchestration` chat, `delegate` returned a running job immediately, the parent performed independent calculations and documentation work, and an automatic hook message delivered `READY_DESKTOP 105`. A subsequent `message` to that job omitted the original token and numbers. Its automatic response recalled `DESKTOP_ORCHID_9417_XQ 37 68 105 2516`. Both responses carried ACP session `ses_ed3dab51affe3WMTLH033HQoEi` and conversation `c2877930-2b3e-43a3-a7bd-6da2c68ff9b7`. No status/drain/wait polling, manual result collection, or extra user prompt occurred between delegation and either completion. This proves active-turn delivery and completed-worker followup in the actual desktop chat; it does not prove idle wakeup, which remains unsupported.
